Build a production-ready MVP for a visual book platform.

WORKING PRODUCT CONCEPT

This product is a hybrid of Kindle and Netflix for books.

The consumer experience should be extremely simple:

Search for a book title → open the book → see chapters → press play → stop anytime → resume later.

The product converts books into AI-generated visual editions.

Do NOT design this like a social network.
Do NOT create a complicated streaming-service homepage.
Do NOT create a cluttered dashboard.

Think:

Kindle simplicity
+
Netflix playback
+
AI-generated visual learning and storytelling.

The core product philosophy is:

GENERATE ONCE.
CATALOG FOREVER.
IMPROVE CONTINUOUSLY.

Once a visual edition of a book is created, it becomes part of the permanent catalog.

Future users should stream the existing visual edition rather than regenerate the same book.

Viewer behavior and feedback should be used to improve weak chapters or scenes over time.

For nonfiction, generate:

The Book Engine should output structured JSON that the rest of the system can use.

11. GENERATE ONCE ARCHITECTURE
--------------------------------------------------

This is extremely important.

If Frankenstein has already been generated, do NOT regenerate Frankenstein because another user searches for it.

The existing visual edition should open immediately.

Generation should only occur when:

A new title is approved
A new licensed edition is being created
A chapter needs revision
A scene needs revision
A major visual-edition upgrade is approved

Store completed media in persistent object storage/CDN.

32. IMPORTANT ENGINEERING RULES
--------------------------------------------------

Do not build everything inside giant files.

Use clean modular architecture.

Separate:

UI
Database
Business logic
AI orchestration
Media processing
Rights logic
Analytics

Use typed schemas.

Validate all structured AI responses.

Use job queues for expensive generation.

Generation tasks must survive page refreshes.

Never make long AI generation depend on a browser tab staying open.

Implement retry logic.

Log provider errors.

Store prompt/version metadata.

Store model used for each generated asset.

Keep secrets in environment variables.

Never expose API keys client-side.

--------------------------------------------------
35. SUCCESS CRITERIA
--------------------------------------------------

V1 succeeds when:

A user can search for Frankenstein.

The book opens.

The user can see chapters.

The user can play a visual chapter.

They can stop.

They can come back.

The application remembers exactly where they stopped.

The visual edition exists once in the catalog.

Admin can inspect the underlying chapters and scenes.

Admin can replace one scene with a better version without regenerating the entire book.

Admin can see how much generation cost.

Viewer feedback can identify weak scenes.

The architecture can eventually accommodate licensed copyrighted books without being rebuilt.

--------------------------------------------------
36. FINAL PRODUCT PRINCIPLE
--------------------------------------------------

Do not optimize for the number of features.

Optimize for the quality of the core transformation:

BOOK
→ UNDERSTAND
→ STRUCTURE
→ VISUALIZE
→ WATCH
→ LEARN
→ IMPROVE

The application interface should remain almost invisible.

The catalog becomes more valuable every time a title is created and every time an existing visual edition becomes better.
